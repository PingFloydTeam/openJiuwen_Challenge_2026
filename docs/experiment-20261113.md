# Эксперимент: композиция инструментов и исправления ревью

Бейзлайн — опубликованное решение `121f6c14fed39a00ad455d809577f484024b09ab`, ранее набравшее 219/233 на старом авторском наборе. Его runtime-файлы побайтово совпадают с замороженным baseline нового эксперимента. Первоначальная гораздо более слабая версия с 62/233 здесь не используется как бейзлайн.

## Дизайн

`bench.intelligence` создаёт английские условия, отдельные oracle и hidden tests. Агент получает только `tasks/`, без `expected`, эталонов и метаданных генератора. Проверка происходит после прогона; сохранность task.json и публичных тестов проверяется хешами, OUT сверяется с answer.txt. Для coding добавлен независимый обычный unittest в отдельном Docker-контейнере, не использующий наш worker.

- Разработка: 40 задач, по 10 каждого типа, 20% нерешаемых, seed 2026111203.
- Первый контроль: 100 задач, по 25 каждого типа, 24% нерешаемых, seed 2026111217. Композиции отличаются от development. Кандидат v2 зафиксирован до прогона. После анализа ошибок этот набор стал регрессией.
- Подтверждающий набор: 100 задач, 24% нерешаемых, seed 2026111301, создан после фиксации runtime v3. Это новые экземпляры тех же контрольных семейств, **не независимый набор новых семейств**. Его результаты не использовались для изменения зафиксированного runtime. В публикуемый исходник после заморозки добавлена только проверка Landlock ABI ≥3: на более старых ядрах запрещены файловые syscalls, поскольку они не защищают truncate. Эта проверка не меняет ветку протестированного ABI 8; после неё повторены все 110 регрессий и официальные примеры. Точная экспериментальная версия сохранена в `candidate-v3-runtime.zip`.

В обоих вариантах: настоящий openJiuwen, Qwen `qwen3.8-27b-noreason`, temperature 0, одна сессия, Docker Linux arm64, 4 CPU, 16 GB RAM, read-only rootfs, tmpfs 2 GB, cap-drop ALL, no-new-privileges, до 512 процессов. В v3 при большом свободном бюджете разрешён ограниченный второй проход `qwen3.8-27b`; это часть сравниваемой политики, а не сравнение одной и той же модели с единственной изменённой подсказкой. Лимит времени подтверждающих прогонов: 1500 с для большого бюджета, 700 с для малого.

Все расходы ниже — подтверждённое usage настоящего API, `input/10 + output`, включая reasoning по схеме прокси. Неизвестный резерв показывается отдельно. Тестовые HTTP-ответы используются только в регрессионных проверках и не включены в живые результаты. Пропуск нерешаемой задачи не приносит баллов.

## Какие задачи и почему

Это правдоподобные усложнения четырёх разрешённых типов, а не сведения о скрытом наборе жюри. Официальные восемь примеров не позволяют установить частоты таких семейств или гарантировать, что каждое появится в финале.

| Тип | Усложнение | Что проверяет |
|---|---|---|
| math | Дробная целевая функция, ограниченные целые, остатки, число допустимых комбинаций; искомый инвариант при неединственных переменных | Сохранение цели и всех ограничений; точное вычисление; различие между неоднозначностью переменных и ответа |
| search | История с часовыми поясами и cutoff, равные UTC-моменты, соединение справочников, идентификаторы с ведущими нулями | Корректность времени, полный просмотр кандидатов, сохранение ties и строковых ключей |
| data_analysis | Сумма максимумов по группам; сумма положительных групп после агрегации; join→group→rank; точное взвешенное среднее | Порядок операций и композицию, которую один узкий агрегатор не выражает |
| coding | Евклидов остаток для отрицательных чисел, сортировка с сохранением повторов и iterable-входа, ceiling на огромных целых, функции из рекуррентного свойства | Скрытые границы, которые не покрывает один публичный пример; обобщение вместо копирования ожидаемого ответа |
| Нерешаемые | Противоречивые ограничения, разные ответы у равноприоритетных записей, отсутствующая необходимая политика/курс/значение | Способность отличить отсутствие данных от ошибки собственного плана; отсутствие ложных ответов |

Названия функций, столбцов, сущностей и численные параметры генерируются. Половина контрольных coding-условий сформулирована прозой без формального универсального assert: так проверка не сводится только к поддержанному парсеру свойств. Скрытые тесты включают отрицательные и очень большие числа, повторяющиеся элементы, итераторы и неизменность входов. До подтверждающего запуска все 19 эталонных coding-реализаций прошли независимый judge.

## Что изменено и зачем

1. **Типизированный составной план.** Модель выбирает операции и их порядок; локальная среда исполняет фильтры, группировки, joins и ранжирование с точными дробями и UTC-временем. Один вызов может заменить несколько обсуждений промежуточных таблиц. Числа, идентификаторы и даты больше не смешиваются.
2. **Проверка цели и памяти.** Для поддержанного класса явных математических условий проверяются цель, режим, уравнения и домены. Компактная память удерживает успешные факты после ошибок. Проверка схемы Pydantic дополнена ограниченными семантическими обязательствами; полного доказательства перевода английского условия нет.
3. **Проверки свойств кода.** Из явных универсальных условий строятся ограниченные проверки, а не ответы по имени функции. Большие целые помогают выявлять потерю точности. Дополнительные проверки модели исполняются; необоснованное «публичные тесты зелёные» не достаточно для принятия неизменённого кода.
4. **Восстановление вместо преждевременного пропуска.** Ошибка соответствия полей возвращает задачу модели. Поддержаны эквивалентный конечный перебор, расширение цепочек подтверждённых сущностей, ограниченные повторы транспорта и второй проход при свободном бюджете.
5. **Проверяемая среда.** Landlock дополняет seccomp, разрешая нужные файловые операции в staging. Независимый coding-judge уменьшает риск общей слепой зоны проверяющей программы и агента.

Это комбинация известных подходов с инженерной адаптацией к лимитам конкурса, а не утверждение о научной новизне. Разделение понимания и исполнения связано с [PAL](https://proceedings.mlr.press/v202/gao23f.html). Проверка промежуточного представления и обратная связь по ошибкам помогают переносить решение между композициями; наличие `Fraction` само по себе не гарантирует правильность выбранного плана.

По той же причине полезен [ReWOO](https://arxiv.org/abs/2305.18323): отделение плана от наблюдений уменьшает повторную передачу контекста. Наш составной `record_plan` применяет близкий принцип, но не воспроизводит весь ReWOO. Следующий эксперимент — исправление только неудачного шага плана с сохранением проверенных зависимостей. Чужие коэффициенты экономии на наши модели и задачи не переносятся. Сравнение при равном бюджете мотивировано также [Reasoning in Token Economies](https://aclanthology.org/2024.emnlp-main.1112/): увеличение сложности стратегии не гарантирует преимущество перед более простым способом потратить те же ресурсы.

## Что осталось улучшить

Приоритет — проверять соответствие плана **всему** вопросу: единицы, валюты, полноту данных и условия отбора. Исполнимый точный план всё ещё может отвечать не на тот вопрос. Ложные ответы на нерешаемые задачи не устранены.

Далее — независимые перефразировки и новые семейства, повторные прогоны и абляции отдельных изменений при одинаковых лимитах. По текущему парному эксперименту нельзя приписать весь прирост одному компоненту или заявить статистическую устойчивость. Для планировщика полезнее измерять предельные баллы за дополнительный бюджет на новых задачах, чем сразу заменять его энкодером.

Для coding стоит расширять проверяемые свойства и поиск минимальных контрпримеров, не угадывая полный контракт по имени функции. Для математики перспективен ограниченный SMT backend с проверкой второго решения искомой величины. Пакетирование независимых коротких задач и локальная небольшая модель остаются отдельными гипотезами: они пока не включены. Сначала нужно измерить их качество, CPU-время и полный размер образа.

## Проверка требований

110 регрессионных тестов финального исходника прошли в Linux arm64. Официальные примеры: 8/8, 20/20 баллов, 0 API-токенов. Сборка amd64 без кеша установочных слоёв: **159,28 с** при уже имеющемся базовом образе; размер после загрузки **1,36 GB** по `docker images`. Эти измерения соответствуют лимитам 1000 с и 4 GB на данной машине, но не гарантируют скорость сети жюри.

Нативное выполнение amd64 не проверено. Под эмуляцией Docker на этом Mac worker выдаёт `seccomp load failed`; защита не отключалась. Нативный arm64 работает. Ядро без Landlock ABI ≥3 оставляет строгую изоляцию без файлового ввода-вывода. Подробности и регистрационная утилита организаторов описаны в [разборе ревью](review-response-20261113.md).

Машинные сводки и траектории публикуются в `benchmarks/intelligence-20261113/`. Генераторы и команды находятся в README. Полные входы и эталоны воспроизводятся через seed; runtime Docker не содержит bench/oracle.
