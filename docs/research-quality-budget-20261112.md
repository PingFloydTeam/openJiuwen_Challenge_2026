|---|---|

| Короткий контекст и кеш | В очередной запрос включаются последние два сообщения обратной связи. Повторные одинаковые вызовы локальных инструментов в некодовых задачах берутся из кеша. Сам повторный запрос LLM по-прежнему расходует токены. |
| Проверки coding | Временная копия, компиляция, публичные unittest, извлечение явных примеров из условия через AST, необязательные дополнительные проверки. После неудачной правки обновляется показанный модели исходник. Это не доказательство прохождения скрытых тестов. |
| Планировщик | Приоритет reward × оценка успеха / оценка цены. Цена обновляется по usage и типу задачи. Вероятность успеха берётся из калибровки или априорного значения, не обучается онлайн по ответам жюри. |

Такое разделение понимания и вычисления близко к PAL: LLM создаёт исполняемое представление, среда вычисляет результат. Это известный подход, а наше инженерное преимущество — специализированные компактные и проверяемые операции. [PAL, ICML 2023](https://proceedings.mlr.press/v202/gao23f.html).

**1. Первый приоритет: единый типизированный язык планов**

Развить существующий `record_plan`: явные типы identifier/string/integer/decimal/date/datetime, последовательные where/latest/join/group/aggregate/argmax и явная цель ответа. Перед исполнением проверять наличие полей, совместимость типов, доступность результатов предыдущих шагов. Даты с часовыми поясами нормализовать как время; идентификатор `0012` сохранять строкой. Не менять порядок where/latest, не сворачивать неоднозначные ties.

Небольшой компилятор должен превращать корректные композиции в имеющиеся точные операции. Исправлять локально можно только однозначные формы записи. Ошибка типа должна выдавать короткую диагностику с допустимыми вариантами, а не молча менять смысл плана.

PICARD показывает пользу синтаксических ограничений при генерации SQL. У нас нет подтверждённого управления декодером прокси, поэтому переносим идею в локальную валидацию и ограниченный язык. JSON-режим, даже если доступен, сам по себе не проверяет правильность операции. [PICARD, EMNLP 2021](https://aclanthology.org/2021.emnlp-main.779/).

**2. Первый приоритет: проверять связь ответа с целью**

Сейчас совпадение ответа с результатом инструмента не всегда означает, что решена задача. Предлагается сохранять объект результата: цель, использованные ограничения, источники, тип проверки, статус и при необходимости контрпример. Вычисление `calc("71")` не должно подтверждать неизвестное x только потому, что получилось число.

Для математического плана проверять единственность именно искомого выражения. Например, при x+y=71 значение x не единственно, а x+y единственно. Для источников проверять согласованность всех подходящих записей и происхождение итогового поля.

Добавить различимые статусы: solved, proven_underdetermined, invalid_plan, unsupported, resource_limit. Ошибка парсера или таймаут не доказывают нерешаемость исходной задачи. Подтверждённую неоднозначность можно завершать локально; неподтверждённый план отправлять на исправление.

Основа — взаимодействие генератора с внешним проверяющим компонентом из LLM-Modulo. Критическое ограничение: проверяющий доказывает свойства формализованной задачи. Неполный перевод английского в ограничения способен дать ложное доказательство. Нужны привязка ограничений к тексту и отдельная проверка полноты. [LLM-Modulo, 2024](https://arxiv.org/abs/2402.01817).

**3. Второй приоритет: Z3 для ограничений, которые неудобно перебирать**

Оставить быстрые текущие решатели, подключить SMT только к поддержанным целочисленным/рациональным формам. Для вопроса о единственном значении сначала получить допустимое решение и значение v, затем проверить совместимость условий с target != v. Второе допустимое решение показывает неоднозначность. UNSAT второго запроса при SAT первого подтверждает единственность в данной формализации. UNKNOWN и таймаут не являются UNSAT.

Проверка максимума, подсчёт решений и нелинейные выражения требуют отдельных методов, их нельзя выдавать за тот же алгоритм. Семантику отрицательного деления, остатка и нулевого знаменателя нужно согласовать с задачей. [Официальная документация Z3](https://microsoft.github.io/z3guide/docs/logic/basiccommands/).

**4. Второй приоритет: выбирать следующий шаг по ожидаемой пользе**

Существующий планировщик знает в основном тип и длину задачи. Предлагаемые признаки: число таблиц, соединений, переменных, объём исходников, доступность тестов, число неоднозначностей и характер последней ошибки. Обучить маленькую регрессию/дерево на тренировочных прогонах. В финале не считать сохранённый ответ доказанным успехом и не использовать скрытые метки.

Оценивать для каждого действия reward × ожидаемый прирост вероятности правильного решения / дополнительные токены. Выбирать между новым заданием, одной коррекцией плана и обращением к другой разрешённой модели. Модели должны разделять единый бюджет. Переход на reasoning оправдывать сигналами проверки и измеренной окупаемостью, а не одним названием категории.

Исследование Snell et al. подтверждает зависимость полезной стратегии от сложности, но оценка сложности в его экспериментах требует большого числа образцов; соответствующие затраты не включены в основной анализ. Для нашего бюджета такая процедура не подходит. [Scaling LLM Test-Time Compute Optimally, §3.2 и Appendix C](https://arxiv.org/html/2408.03314v1).

**5. Второй приоритет: выполнять цепочку без LLM между каждым шагом**

Расширить уже существующее локальное исполнение record_plan до небольшого графа зависимостей: независимые чтения, затем точное вычисление, затем проверка. Передавать результаты по ссылкам на узлы, а не переписывать их текстом через LLM. Повторно обращаться к модели только при неизвестной ветке или ошибке.

LLMCompiler исследует планировщик, диспетчер и исполнитель с зависимостями. У нас главная гипотеза экономии — уменьшение числа запросов и передачи промежуточных результатов. Само распараллеливание сокращает задержку, но не обязано уменьшать токены. [LLMCompiler, ICML 2024](https://arxiv.org/html/2312.04511v3).

Отдельный эксперимент — пакет из 2–4 коротких однотипных задач в одном запросе с общей схемой инструмента. Ответы, источники и ошибки строго привязывать к task_id. Большие coding-задачи в такой пакет не включать. Учитывать цену повторов повреждённого пакета.

**6. Второй приоритет: краткое состояние вместо последних двух сообщений**

Хранить локально известные типы, выбранные источники, цель, проверенные ограничения, последнюю ошибку и ещё не проверенные требования. Формировать компактное состояние детерминированно. Сейчас старый, но важный результат может выпасть из последних двух сообщений. Подтверждённые факты не должны теряться, а одинаковые ошибки не должны запускать новый цикл.

Для файлов показывать схему и релевантные поля, оставляя полные данные локальным инструментам. Для больших текстовых баз можно отдельно испытать локальный лексический индекс; выбор нескольких найденных фрагментов ещё не доказывает отсутствие конфликтующих записей. Исследование Lost in the Middle мотивирует аккуратный отбор контекста, но не даёт готовой оценки экономии на нашем Qwen. [Lost in the Middle](https://arxiv.org/abs/2307.03172).

**7. Третий приоритет: свойства и минимальные контрпримеры для coding**

Использовать Hypothesis для поддержанных контрактов: сортировка сохраняет мультимножество и упорядочивает, encode/decode возвращает исходное значение, идемпотентная нормализация выдерживает повторное применение. Для маленьких входов можно сопоставлять с независимо заданным простым алгоритмом. Свойство должно следовать из условия; тест, придуманный LLM, тоже может быть неверен.

Модель получает минимальный контрпример после shrinking. Публичные тесты остаются неизменными. Наш прошлый эксперимент с обязательной LLM-генерацией дополнительных тестов оказался невыгодным, поэтому предлагается ограниченная локальная проверка, запускаемая при подходящем контракте. [Hypothesis](https://hypothesis.readthedocs.io/en/latest/), [объяснение shrinking авторами](https://hypothesis.works/articles/integrated-shrinking/).

**8. Локальная модель как отдельная гипотеза**

В сообщении пользователя передано разрешение организаторов на локальные модели. Оно отличается от исходного файла регламента, содержащего запрет; предложение опирается на переданное уточнение. Сейчас локальной LLM в рабочем решении нет.

Возможный эксперимент — небольшая квантованная модель для выбора инструмента и построения типизированного плана, с той же внешней проверкой и переходом к прокси при неудаче. llama.cpp поддерживает CPU и квантование. Но при 4 CPU, 16 GB RAM, отсутствии GPU, лимите образа 4 GB и часовом запуске оценивать нужно одновременно API-токены, время, память и число правильных задач. Веса, runtime и KV-кеш — разные статьи ресурсов. Выбор конкретной модели делать после измерения в Linux-контейнере. [llama.cpp](https://github.com/ggml-org/llama.cpp).

**Что не ставить первым**

Массовые дебаты агентов, длинная саморефлексия и несколько решений каждого задания увеличивают расход без гарантии прироста. В Reasoning in Token Economies сложные стратегии сравниваются с простыми при равном бюджете, и преимущество сложности не универсально. [EMNLP 2024](https://aclanthology.org/2024.emnlp-main.1112/).

Не рассчитывать на экономию конкурсных токенов от кеша провайдера: регламент её явно исключает. Не разрастаться в новые regex под каждый провал. У текущих локальных шаблонов есть польза на распознанных формах, но следующий прирост обобщения должен идти через композицию и проверку планов.

**Как проверять предложения**

Новый бейзлайн — нынешняя версия с 219/233, а не первоначальная с 62/233. Старые 100 задач остаются регрессией: мы уже разобрали их ошибки, поэтому они больше не являются независимой проверкой следующих правок.

Для каждого изменения отдельно: разработка → заморозка → новые семейства задач → одинаковые бюджеты и модели. Контроль: 100 английских задач, по 25 на сегмент, 6 нерешаемых в каждом, итого 24%. Разделять семейства и композиции между development и test, не только случайные числа. Варьировать названия колонок, порядок условий, даты/часовые пояса, ties, пустые значения, несколько файлов и граничные случаи кода. Каждая задача и её эталон должны быть отдельно проверены на соответствие правилам и отсутствие случайной неоднозначности.

Сравнивать при 5000, 20000 и 100000 выходных эквивалентов, желательно не менее трёх повторов. Главная метрика — баллы при фиксированном бюджете, затем расход при сопоставимом качестве. Дополнительно: пропуски решаемых, ложные ответы на нерешаемые, типы ошибок, число запросов, стоимость проверки, время и пик памяти. Нерешаемость сама по себе баллов не приносит. Linux/Docker-проверка нужна до выводов о готовности к финалу.

Практическая последовательность: типизированный план и цель → различение ошибок и доказанной неоднозначности → новый честный контроль → SMT и планировщик → свойства кода, пакетирование и локальная модель при подтверждённой пользе.
