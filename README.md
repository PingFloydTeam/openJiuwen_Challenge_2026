# Ping Floyd · openJiuwen Challenge 2026

Харнесс команды Ping Floyd решает задачи четырёх типов: `math`, `search`, `data_analysis` и `coding`. Для каждой задачи openJiuwen 0.1.19 запускает workflow `Start → Solve → Save → End`. Сначала харнесс пробует локальное решение. Если данных достаточно, но локальный алгоритм не подходит, планировщик выбирает задачу для обращения к модели. Модель составляет план или вызывает инструмент, а вычисления и проверка выполняются локально.

Новая проверка в Linux: 100 английских задач, 24% нерешаемых, скрытые coding-тесты. Бейзлайн — опубликованный `121f6c1`. Результаты одного парного эксперимента:

| Бюджет | Бейзлайн: баллы / расход | Улучшения: баллы / расход |
|---:|---:|---:|
| 5 000 | 59/239 · 4 860,3 | 98/239 · 4 858,0 |
| 100 000 | 141/239 · 23 961,3 | 201/239 · 37 199,5 + резерв 930,6 |

Расход — выходные эквиваленты. Экономия при большом бюджете не заявляется: первый проход дал 198 баллов за 27 388,6, а второй добавил 3 балла за 9 810,9. Coding: 9→18 правильных из 19, подтверждено независимым unittest. Финальные исходники проходят 110 регрессионных проверок и 8/8 официальных примеров. [Методика, ограничения и разбор ошибок](docs/experiment-20261113.md), [замороженные входы, версии и траектории](benchmarks/intelligence-20261113/).

## Сборка и запуск

```sh
docker build --target contest -t ping-floyd:contest .
```

Базовый образ Python 3.13.7 зафиксирован по digest, зависимости закреплены в `requirements.txt`. Они устанавливаются при сборке. Во время прогона харнесс обращается только к API по `LLM_BASE_URL`. Для сборки и проверки локально нужен Docker с Linux-контейнерами.

Организаторы передают `LLM_BASE_URL` и `LLM_API_KEY` через окружение. Для ручного прогона экспортируйте их в оболочке и используйте отдельную копию задач с доступом на запись. Пример запуска в сети организаторов `hack-net`:

```sh
mkdir -p "$PWD/out"
docker run --rm --network hack-net \
  -e LLM_BASE_URL -e LLM_API_KEY -e BUDGET=100000 \
  -e HOME=/tmp -e OUT=/out/answers.txt \
  -v "$TASKS:/data/tasks:rw" -v "$PWD/out:/out:rw" \
  --read-only --tmpfs /tmp:rw,size=2g \
  --cap-drop ALL --security-opt no-new-privileges \
  --cpus 4 --memory 16g --pids-limit 512 \
  ping-floyd:contest --tasks-dir /data/tasks
```

| Параметр | Назначение |
|---|---|
| `TASKS` или `--tasks-dir` | Каталог с подкаталогами задач. В каждом лежит `task.json`, а входные файлы находятся в `workspace/`. |
| `OUT` или `--out` | Необязательный общий файл решений или существующий каталог, в котором создаётся `answers.txt`. |
| `BUDGET` или `--budget` | Общий бюджет в выходных эквивалентах. Значение по умолчанию 100 000. |
| `LLM_BASE_URL`, `LLM_API_KEY` | Базовый URL и ключ прокси. К URL добавляется `/chat/completions`. |
| `--model`, `--workers`, `--seconds` | По умолчанию `qwen3.8-27b-noreason`, одна сессия и 3500 секунд. Допустимо от одной до пяти сессий. |
| `--offline`, `--trace` | Локальный прогон без LLM и дополнительный путь для журнала JSONL. События также идут в stdout. |
| `--retry-model`, `--retry-share`, `--no-auto-retry` | Вторая разрешённая модель для застрявших задач. Автоматически: при бюджете от 25 000 и остатке ≥50% после первого прохода; максимум 10% исходного бюджета. Последний флаг отключает автоматический проход. |

Ответ сохраняется атомарно в `answer.txt` рядом с `task.json`. Для проверенного coding-решения харнесс переносит изменения исходников из временной копии и записывает `DONE`. При пропуске файл ответа отсутствует. При заданном `OUT` общий снимок обновляется после каждого сохранения. Формат снимка — UTF-8 TSV с полями `task_id` и `answer`, без заголовка. При повторном запуске существующие ответы пропускаются, а снимок восстанавливается из них.

## Как расходуется бюджет

Локальные алгоритмы выполняются первыми и расходуют ноль токенов модели. Для оставшихся задач приоритет определяется как `reward × оценка вероятности решения / оценка стоимости`. Начальная стоимость зависит от типа и длины условия. По вызовам с подтверждённым `usage` оценка стоимости обновляется скользящим средним.

Расход считается в десятых долях выходного токена по формуле `input_tokens + 10 × output_tokens`. Токены рассуждения учитываются в выходе согласно формату `usage` прокси. Перед запросом харнесс резервирует оценку входа и максимальный выход в рамках общего бюджета и лимита задачи. Если ответ не содержит достоверного `usage`, резерв учитывается отдельно. Счётчик общий для всех сессий. Ограничения времени, шагов и попыток исправления ограничивают расход на одну задачу. Повторяющиеся пустые ответы прокси прекращают обращения к модели.

Временный HTTP 429 с подходящим `Retry-After` и усечённый ответ допускают ограниченный повтор. Расход и резерв первой попытки сохраняются. Несогласованное `total_tokens` не принимается за достоверный меньший расход. Кеш провайдера не даёт скидки на конкурсный бюджет. Подтверждённые локальными инструментами факты сохраняются в ограниченной памяти задачи, включая последние ошибки; одинаковые вычисления повторно не выполняются.

## Как определяются нерешаемые задачи

- **Математика.** Точные дроби, исключение переменных и ограниченный перебор помогают выявить противоречия и проверить единственность искомого значения.
- **Поиск и анализ данных.** `record_plan` выполняет типизированные фильтры, выбор ревизий, соединения, группировки, ранжирование и агрегацию в заданном порядке. Идентификаторы остаются строками, даты проверяются, временные метки приводятся к UTC. Равноприоритетные записи сохраняются; неоднозначность оценивается по запрошенному результату. Неподдержанное имя поля — повод исправить план, а не доказательство невозможности всей задачи.
- **Код.** Правки проходят компиляцию, публичные `unittest` и проверки поддержанных явных контрактов в отдельной копии. Универсальные свойства проверяются на ограниченном наборе граничных входов, включая большие целые; изначально зелёный неизменённый код требует дополнительных исполнимых проверок. Это не гарантия скрытых тестов. Публичные тесты остаются неизменными.
- **Пропуск.** При доказанной неоднозначности, отсутствии данных или исчерпании лимита без подтверждённого решения харнесс оставляет задачу без ответа. Эвристики пропуска могут ошибаться, что видно по результатам ниже.

## Эксперименты и траектории

Архивный эксперимент 12 ноября, до текущих исправлений (commit `121f6c1`). На авторском контрольном наборе из 100 английских задач было по 25 задач каждого типа, из них 24 нерешаемые. Сравнивались исходная версия и финальный харнесс на одной модели `qwen3.8-27b-noreason`, с одной сессией и одинаковыми входами. Ниже выходные эквиваленты равны `output_tokens + input_tokens / 10`.

| Бюджет | Баллы исходной версии | Баллы финальной версии | Расход исходной версии | Расход финальной версии |
|---:|---:|---:|---:|---:|
| 100 000 | 62/233 | 219/233 | 21 964,7 | 16 618,1 |
| 5 000 | 0/233 | 90/233 | 4 811,4 | 4 878,2 |

В основном прогоне финальная версия решила 69 из 76 выполнимых задач, пропустила семь и один раз ответила на нерешаемую. Восемь официальных примеров дали 20/20 в режиме без LLM. Результаты получены на macOS с одним и тем же адаптером запуска тестов для обеих версий. Тот эксперимент не проверял выполнение под ограничениями Linux; новая проверка приведена ниже.

В [траекториях](benchmarks/trajectories/) доступны события вызовов, имена инструментов, расход токенов и результаты по задачам. [Сводка](benchmarks/summary.json) содержит параметры прогонов и результаты проверки. Для повторения контрольного эксперимента:

```sh
docker build --target bench -t ping-floyd:bench .
python3 -m bench.frontier /tmp/ping-floyd-transfer
python3 -m bench.validation /tmp/ping-floyd-transfer /tmp/ping-floyd-run \
  --image ping-floyd:contest --bench-image ping-floyd:bench \
  --live --budget 100000 --seconds 3500
```

Генератор создаёт входы и эталоны отдельно. При эксперименте харнесс получает только каталог задач, а отдельный проверяющий процесс использует эталоны после прогона. Для локальной проверки без прокси уберите `--live`.

## Проверки и ограничения новой версии

[Отчёт эксперимента 13 ноября](docs/experiment-20261113.md) сравнивает эту версию с опубликованным `121f6c1` на более сложных композициях четырёх типов, с 24% нерешаемых. [Разбор независимого ревью](docs/review-response-20261113.md) связывает замечания R01–R12 с исправлениями, проверками и оставшимися ограничениями. [Исследовательская записка](docs/research-quality-budget-20261112.md) содержит первичные источники и направления дальнейшей работы.

```sh
docker build --target bench -t ping-floyd:bench .
docker run --rm --network none --read-only --tmpfs /tmp:rw,size=2g \
  --cap-drop ALL --security-opt no-new-privileges \
  --cpus 4 --memory 16g --pids-limit 512 -e HOME=/tmp \
  --entrypoint python ping-floyd:bench \
  -m unittest discover -s bench -t /app -p '*checks.py' -q

python3 -m bench.intelligence /tmp/ping-floyd-new --seed 2026111301
python3 -m bench.validation /tmp/ping-floyd-new /tmp/ping-floyd-new-run \
  --image ping-floyd:contest --bench-image ping-floyd:bench \
  --live --budget 100000 --seconds 1500
python3 -m bench.independent_coding /tmp/ping-floyd-new-run/suite \
  --image ping-floyd:bench
```

Последняя команда запускает скрытые coding-тесты обычным `unittest` в отдельном контейнере на задачу, независимо от worker харнесса. Для проверки эталонов до прогона используйте исходный `/tmp/ping-floyd-new` и `--reference`. Эталоны и bench-модули не входят в финальную стадию `contest`.

В Linux worker использует seccomp и, если ядро поддерживает Landlock ABI ≥3, Landlock: чтение/запись своих файлов разрешены в staging, stdlib доступна для чтения, сеть и создание процессов запрещены. На ядре без Landlock ABI ≥3 остаётся строгий режим без файловых операций. Проверен нативный Linux arm64. Образ amd64 собирается; успешное выполнение coding-worker на нативном amd64 ещё не проверено. Ограничения сборки: 1000 секунд, образ <4 ГБ, репозиторий без `.git` <100 МБ. Холодная сборка зависит от сети; конкретные замеры приведены в отчёте.

Предоставленный организаторами `tools/collect_harness_report.py` сохранён без изменений как необязательная утилита для `agent-registry-mcp`. Он собирает переменные `JIUWENSWARM_*`, родительские процессы и хеш отчёта; при решении задач не запускается и не включён в образ. Использование openJiuwen обеспечивается настоящими `Workflow`/`LocalFunction`, без имитации маркеров окружения.
